## 4.4. 软件工程过程组（SWE）

本节定义从软件需求到软件验证的软件开发生命周期过程，与系统工程（SYS）及后续验证（VAL）形成衔接。

*（架构视角：SWE 与 SYS 的边界在于“系统级”与“软件级”工作产品的划分；HSI、资源与实时性等往往在 SYS 与 SWE 之间反复迭代。）*

---

## 4.4.1. SWE.1 软件需求分析（Software Requirements Analysis）

**过程 ID：** SWE.1  

**过程名称：** 软件需求分析  

**过程目的：**  
建立一套经结构化与分析、且与**系统需求**及**系统架构**相一致的软件需求集合。

**过程结果：**

1. 规定软件需求。  
2. 对软件需求进行结构化并区分优先级。  
3. 分析软件需求的正确性与技术可行性。  
4. 分析软件需求对运行环境的影响。  
5. 在软件需求与系统需求之间建立一致性与双向可追溯性。  
6. 在软件需求与系统架构之间建立一致性与双向可追溯性。  
7. 软件需求经各方达成一致并向所有受影响方沟通。

**基础实践（Base Practices）**

**SWE.1.BP1：规定软件需求。**  
依据定义的需求特征，使用系统需求与系统架构来识别并记录软件的功能性与非功能性需求。  

- 注 1：需求特征可在 IEEE 29148、ISO 26262-8:2018、INCOSE 需求编写指南等标准中定义。  
- 注 2：技术标准中常见的要求特征示例包括：可验证性（需求文本中隐含验证准则）、无歧义/可理解、独立于设计与实现、与其他需求不冲突等。  
- 注 3：在**仅开发软件**的场景中，系统需求与系统架构指向给定的运行环境；此时可用干系人需求作为识别软件能力与功能的基础。  
- 注 4：软硬件接口（HSI）在系统设计中把硬件纳入语境，属于系统设计层面的接口决策；若存在 HSI，可为软件需求提供输入。

*（架构视角：嵌入式项目中，HSI、时序预算、存储与算力约束、安全/诊断相关需求常在此过程与 SWE.2 交错细化；尽早把“可验证的”非功能需求（栈、WCET、启动时间等）写清楚，可减少后期架构返工。）*

**SWE.1.BP2：结构化软件需求。**  
对软件需求进行结构化并区分优先级。  

- 注 5：结构化准则示例：按功能分组、表达产品变型等。  
- 注 6：优先级可按项目或干系人需要通过发布范围等方式确定，参见 SPL.2.BP1。

**SWE.1.BP3：分析软件需求。**  
分析已规定的软件需求及其相互依赖，以确保正确性、技术可行性，并支持项目管理中的项目估算。  

- 注 7：项目可行性参见 MAN.3.BP3，项目估算参见 MAN.3.BP5。  
- 注 8：技术可行性可基于平台/产品线或通过原型等方法评估。

**SWE.1.BP4：分析对运行环境的影响。**  
分析软件需求将对运行环境中各要素产生的影响。

*（架构视角：“运行环境”在嵌入式语境下常包括 ECU、OS/RTOS、BSP、通信栈、电源模式与标定链路；本条强调需求变更对环境与集成策略的波及。）*

**SWE.1.BP5：确保一致性并建立双向可追溯性。**  
在软件需求与系统架构之间、软件需求与系统需求之间，确保一致性并建立双向可追溯性。  

- 注 9：不要求冗余追溯。  
- 注 10：部分非功能性的系统需求可能无法由软件需求追溯覆盖（例如过程类需求或与软件产品生命周期后续阶段相关的需求）；此类需求仍须接受验证。  
- 注 11：双向可追溯性有助于一致性、变更影响分析及验证覆盖的证明；仅有链接不代表信息彼此一致。  
- 注 12：纯软件开发时，可与干系人需求—软件需求之间建立一致性及双向可追溯性。

**SWE.1.BP6：沟通已达成一致的软件需求及对运行环境影响。**  
将已达成一致的软件需求以及对运行环境影响分析的结果，传达给所有受影响方。

## 4.4.2. SWE.2 软件架构设计（Software Architectural Design）

**过程 ID：** SWE.2  

**过程名称：** 软件架构设计  

**过程目的：**  
建立经分析的软件架构，包含**静态**与**动态**方面，并与软件需求一致。

**过程结果：**

1. 设计软件架构，包含静态与动态方面。  
2. 按既定准则分析软件架构。  
3. 在软件架构与软件需求之间建立一致性与双向可追溯性。  
4. 软件架构经达成一致并向所有受影响方沟通。

**基础实践**

**SWE.2.BP1：规定软件架构的静态方面。**  
针对功能性与非功能性软件需求，规定并记录软件架构的静态方面，包括外部接口，以及具有接口与相互关系的、已定义的一组软件构件。  

- 注 1：HSI 将硬件设计纳入语境，属于系统设计（SYS.3）的方面。

*（架构视角：静态架构通常对应分层、模块边界、AUTOSAR 组件/RTE 映射、驱动与中间件切分、存储分区与安全域等；接口契约（数据类型、调用语义、错误模型）是后续详细设计与集成验证的基础。）*

**SWE.2.BP2：规定软件架构的动态方面。**  
针对功能性与非功能性软件需求，规定并记录软件架构的动态方面，包括各软件构件在不同软件模式下的行为及其交互，以及**并发**相关方面。  

- 注 2：并发方面示例：与应用相关的中断处理、可抢占处理、多线程等。  
- 注 3：行为描述可采用自然语言或半形式化表示（如 SysML、UML）。

*（架构视角：嵌入式关键路径往往是任务/中断/核间协作与数据流时序；动态模型应能支撑资源竞争、优先级反转风险与端到端延时预算的 reasoning。）*

**SWE.2.BP3：分析软件架构。**  
就相关技术设计方面分析软件架构，并支持项目管理中的项目估算。记录软件架构设计决策的**依据（rationale）**。  

- 注 4：参见 MAN.3.BP3 / MAN.3.BP5。  
- 注 5：分析可包括既有软件构件对当前应用的适用性。  
- 注 6：可用原型、仿真、定性分析等方法。  
- 注 7：技术方面示例：功能、时序、资源消耗（如 ROM、RAM、片内/片外 EEPROM 或 Data Flash、CPU 负荷等）。  
- 注 8：设计依据可包括沿用证明（proven-in-use）、复用框架/产品线、自制或外购决策、演进式/集式设计等论证。

*（架构视角：将 timing、memory、fault handling 与安全机制在架构层量化，并形成可追溯的 rationale，是满足 ASPICE/SWE.2 与功能安全对齐评审的常见抓手。）*

**SWE.2.BP4：确保一致性并建立双向可追溯性。**  
在软件架构与软件需求之间确保一致性并建立双向可追溯性。  

- 注 9：部分非功能性软件需求可能无法追溯到软件架构（如开发过程类需求）；仍将接受验证。  
- 注 10：同上，可追溯性≠自动一致。

**SWE.2.BP5：沟通已达成一致的软件架构。**  
将已达成一致的软件架构传达给所有受影响方。

## 4.4.3. SWE.3 软件详细设计与单元构建（Software Detailed Design and Unit Construction）

**过程 ID：** SWE.3  

**过程名称：** 软件详细设计与单元构建  

**过程目的：**  
建立与软件架构一致的软件详细设计（含静态与动态方面），并构建与详细设计一致的**软件单元**。

**过程结果：**

1. 规定详细设计（含静态与动态方面）。  
2. 按照详细设计生产出软件单元。  
3. 在详细设计与软件架构、源代码与详细设计、详细设计与软件需求之间建立一致性及可追溯性组合（详见 BP4；其中与软件需求为可追溯性表述）。  
4. 将源代码与已达成一致的详细设计传达给所有受影响方。

**基础实践**

**SWE.3.BP1：规定详细设计的静态方面。**  
对每个软件构件，规定其软件单元的**行为**、静态结构及关系，以及单元接口，包括：

- 输入与输出的合法数据取值范围（**应用领域视角**）；  
- 适用于输入输出的物理或计量单位（**应用领域视角**）。

- 注 1：软件单元边界**不**由其源代码表现形式、代码文件结构或基于模型的实现方式决定，而由应用领域语义驱动；因而在代码层面，一个单元可对应单子程序或多子程序集合。  
- 注 2：应用领域取值示例：`0..200 [m/s]`、`0..3.8 [A]`、`1..100 [N]`；与语言层数据类型映射见 BP2 相关实践语境（原文在 Note 2 指向 BP2）。  
- 注 3：计量单位示例：`%`、`‰`。  
- 注 4：计数器等参数或返回值可能没有物理或计量单位。  
- 注 5：HSI 属 SYS.3 方面。

*（架构视角：这一条把“物理语义”推到详细设计显性化，便于后续单元测试与安全分析中的边界与饱和；也是模型到代码一致性的锚点。）*

**SWE.3.BP2：规定详细设计的动态方面。**  
针对软件架构，规定并记录详细设计的动态方面，包括为满足构件动态行为所需的、相关软件单元之间的交互。

- 注 6：行为描述可使用自然语言或 SysML、UML 等半形式化方式。

**SWE.3.BP3：开发软件单元。**  
按照详细设计及编码准则开发与记录软件单元。  

- 注 7：能力等级 1 下编码准则示例：避免隐式类型转换；子程序单入口单出口；范围检查（契约式设计、防御式编程）；更多示例见 ISO 26262-6 条款 8.4.5 及表 6。

*（架构视角：在嵌入式栈中，常与 MISRA、CERT、Autosar coding、静态分析门禁结合；防御式代码与清晰的单元边界有助于 SWE.4 的度量选择（审查/静态分析/单元测试）分层。）*

**SWE.3.BP4：确保一致性并建立双向可追溯性。**  
在详细设计与软件架构之间、已开发软件单元与详细设计之间，确保一致性并建立双向可追溯性；在详细设计与软件需求之间建立可追溯性。  

- 注 8：应通过上述方式的组合避免冗余。  
- 注 9：软件单元可直接追溯到需求的示例：通信矩阵；或 AUTOSAR 配置中固有的诊断标识符列表等基础软件侧面信息。  
- 注 10：可追溯性与一致性的关系同前。

**SWE.3.BP5：沟通已达成一致的详细设计与已开发的软件单元。**

## 4.4.4. SWE.4 软件单元验证（Software Unit Verification）

**过程 ID：** SWE.4  

**过程名称：** 软件单元验证  

**过程目的：**  
验证软件单元与软件详细设计一致。

**过程结果：**

1. 规定软件单元验证的验证措施（verification measures）。  
2. 按发布范围选择单元验证措施，含回归验证准则。  
3. 用所选措施验证软件单元并记录结果。  
4. 在验证措施与软件单元之间建立一致性与双向可追溯性；在验证结果与验证措施之间建立双向可追溯性。  
5. 汇总软件单元验证结果并传达给所有受影响方。

**基础实践**

**SWE.4.BP1：规定软件单元验证措施。**  
对详细设计中定义的每一软件单元规定验证措施，包括：措施的通过/失败准则；措施的进入/退出准则；所需的验证基础设施。  

- 注 1：示例：静态分析、代码评审、单元测试。  
- 注 2：静态分析可基于 MISRA 规则集及其他编码规范。

*（架构视角：对硬实时与安全相关单元，常以“requirements-based unit test + MC/DC 或结构化覆盖”组合；与时间、资源相关的单元可辅以 Worst-case 分析及在环前的 SIL 占位。）*

**SWE.4.BP2：选择软件单元验证措施。**  
记录验证措施的选择，考虑选择准则（含回归准则）；所载选择须在发布范围内具有足够覆盖。

**SWE.4.BP3：验证软件单元。**  
用所选措施执行单元验证；记录验证结果（含通过/失败状态及验证措施数据）。

- 注 3：与预期不符的结果处理见 SUP.9。

**SWE.4.BP4：确保一致性并建立双向可追溯性。**  
详细设计定义的软件单元与验证措施之间；验证结果与验证措施之间——按条文建立一致性与双向可追溯性。

**SWE.4.BP5：汇总并沟通结果。**  
汇总单元验证结果；摘要中应包含足以让其他方判断后果的执行信息。

- 注 5：摘要信息完整性用于支持他方影响判断。

## 4.4.5. SWE.5 软件构件验证与集成验证（Software Component Verification and Integration Verification）

**过程 ID：** SWE.5  

**过程名称：** 软件构件验证与集成验证  

**过程目的：**  
验证软件构件与**软件架构设计**一致；集成软件要素并验证集成后的软件要素与**软件架构**及**软件详细设计**一致。

**过程结果（摘要）：**

1. 基于架构与详细设计，针对集成后的软件要素，规定软件集成验证措施（含构件间接口与交互）。  
2. 规定软件构件级验证措施，以证明构件行为与接口符合架构中的定义。  
3. 将软件要素集成直至完整集成软件。  
4. 按发布范围选择验证措施（含回归准则）。  
5. 对软件构件执行所选验证并记录结果。  
6. 对集成后的软件要素执行所选集成验证并记录结果。  
7. 在验证措施与架构/详细设计的静态与动态方面之间建立一致性与双向可追溯性；验证结果与验证措施之间双向可追溯。  
8. 汇总构件验证与集成验证结果并沟通。

**基础实践（要点）**

**SWE.5.BP1：规定软件集成验证措施。**  
基于规定的集成**顺序**与**前置条件**，对照架构的静态与动态方面，规定措施，含：技术、通过/失败准则、进入/退出准则、基础设施与环境搭建。  

- 注 1：可聚焦数据流、构件间动态交互与时序依赖、接口数据语义一致性、资源消耗目标符合性等。  
- 注 2：可借助硬件调试接口或 SIL 等仿真环境。

*（架构视角：本条把“集成策略（stub/driver、渐进式、CI）”与验证挂钩；车载软件常在此阶段暴露 RTE/调度/总线负载问题。）*

**SWE.5.BP2：规定用于验证软件构件行为的措施。**  
针对架构中定义的构件行为与接口规定措施（技术、进入/退出、通过/失败、基础设施与环境）。  

- 注 3：措施针对**构件**而非软件单元（单元级在 SWE.4）。

**SWE.5.BP3：选择验证措施。**  
对每个集成步骤记录集成验证措施的选择（含回归）；覆盖须满足发布范围。

- 注 4：选择准则示例：CI/CD 回归需要、交付用途（试验台、试车场、公开道路等）。

**SWE.5.BP4：集成软件要素并执行集成验证。**  
按规定的接口与交互、顺序与前置条件集成至完整软件；执行所选集成验证并记录数据。  

- 注 5：集成启动前置条件示例：既有构件、COTS、开源、自动代码生成软件的合格认定。  
- 注 6：前置条件允许大爆炸式集成、持续集成、跨单元/构件的逐步集成等策略。  
- 注 7：结果偏离处理见 SUP.9。（原文 Note 7 措辞略有笔误，意指 SUP.9。）

**SWE.5.BP5：执行软件构件验证。**  
执行所选构件行为验证措施并记录结果。  

- 注 8：偏离处理见 SUP.9。

**SWE.5.BP6：确保一致性并建立双向可追溯性。**  
验证措施与架构/详细设计的静态与动态方面；验证结果↔验证措施。

**SWE.5.BP7：汇总并沟通结果。**  
汇总构件验证与集成验证结果；摘要应便于他方判断后果。

## 4.4.6. SWE.6 软件验证（Software Verification）

**过程 ID：** SWE.6  

**过程名称：** 软件验证  

**过程目的：**  
确保**集成后的软件**经验证与**软件需求**一致。

**过程结果：**

1. 基于软件需求规定软件验证措施。  
2. 按发布范围选择措施（含回归准则）。  
3. 对集成软件执行所选措施并记录结果。  
4. 在验证措施与软件需求之间建立一致性与双向可追溯性；验证结果与验证措施双向可追溯。  
5. 汇总软件验证结果并沟通。

**基础实践**

**SWE.6.BP1：规定软件验证措施。**  
规定能证明集成软件符合软件需求中功能与非功能信息的措施，包括：技术、通过/失败准则、进入/退出准则、**必要执行顺序**、基础设施与环境。  

- 注 1：技术选择可依需求类型（如边界值/等价类、正向与负向/故障注入）、基于需求的测试与基于经验的错误推测等。

*（架构视角：SWE.6 是典型的“requirements-based testing + HIL/SIL/Bench”层级；非功能需求如性能、容错、降级路径需在此处显式映射到环境与场景，而非仅功能路径。）*

**SWE.6.BP2：选择验证措施。**  
记录选择（含回归）；覆盖满足发布范围。  

- 注 2：准则示例：需求优先级、持续开发、需求变更驱动的回归、交付使用场景（试验台等）。

**SWE.6.BP3：验证集成软件。**  
执行并记录结果（含通过/失败与数据）。  

- 注 3：偏离处理见 SUP.9。

**SWE.6.BP4：确保一致性并建立双向可追溯性。**  
验证措施↔软件需求；验证结果↔验证措施。

**SWE.6.BP5：汇总并沟通结果。**

## 附录 A：基于第一性原理与费曼方式的 SWE.1-SWE.6 分析报告

本章用一个简单但完整的例子来解释 SWE.1-SWE.6：开发一个 `UART HAL` 驱动，使上层软件可以通过统一接口初始化串口、发送数据、接收数据、查询错误，并在必要时通过中断或 DMA 完成收发。

### A.1 第一性原理：SWE 的本质问题

从第一性原理看，软件工程不是为了“写文档”，而是为了回答六个最基本的问题：

1. 我们到底要让软件做到什么？这对应 SWE.1。
2. 软件由哪些大的部分组成，它们如何协作？这对应 SWE.2。
3. 每个部分内部具体怎么实现？这对应 SWE.3。
4. 每个最小可验证的软件单元是否按详细设计工作？这对应 SWE.4。
5. 多个单元或构件组合后是否仍按架构协作？这对应 SWE.5。
6. 完整集成后的软件是否满足最初的软件需求？这对应 SWE.6。

用一句费曼式解释：SWE.1-SWE.6 就像造一个“可证明能工作的积木系统”。先说清楚要拼成什么，再设计积木怎么分，再写出每块积木，再检查每块积木，再检查积木拼起来是否吻合，最后检查整个作品是不是最初想要的东西。

*（架构视角：ASPICE 关注的不是“是否写了代码”，而是“从需求到验证是否形成证据链”。对嵌入式软件来说，最容易丢失证据链的位置通常是接口语义、错误处理、时序约束和回归验证准则。）*

### A.2 用串口 HAL 驱动重新理解 SWE.1-SWE.6

假设系统需求是：ECU 需要通过 UART 与外部诊断设备通信，波特率为 115200 bps，8N1 格式，支持发送和接收，接收异常时能够报告错误，上层调用不能直接访问 MCU 寄存器。

### A.3 SWE.1：把“想要什么”变成可验证的软件需求

SWE.1 的第一性问题是：如果没有代码，单看需求，我们是否知道 UART HAL 应该做什么、什么算成功、什么算失败？

串口 HAL 示例需求：

| 需求 ID | 软件需求 | 验证准则 |
|---------|----------|----------|
| SWE1-UART-001 | UART HAL 应提供 `Uart_Init(channel, config)` 接口，用于初始化指定通道。 | 给定合法配置，调用后 UART 寄存器配置与 `config` 一致，并返回 `UART_OK`。 |
| SWE1-UART-002 | UART HAL 应支持 `115200`、`9600` 两种波特率。 | 在测试环境中读取配置寄存器或仿真桩，确认分频配置正确。 |
| SWE1-UART-003 | UART HAL 应提供非阻塞发送接口 `Uart_Transmit(channel, data, length)`。 | 当发送缓冲空闲时，接口在 `100 us` 内返回，后续由中断或轮询推进发送。 |
| SWE1-UART-004 | UART HAL 应检测接收溢出、帧错误、奇偶校验错误，并向上层报告。 | 注入错误标志后，上层可通过回调或查询接口获得对应错误码。 |
| SWE1-UART-005 | UART HAL 不允许上层直接访问 UART 外设寄存器。 | 架构和代码审查确认寄存器访问仅存在于驱动底层模块。 |

费曼式理解：SWE.1 不是写“我要一个串口驱动”，而是写“谁调用、传什么、什么时候返回、错了怎么办、如何证明它做到了”。

*（架构视角：HAL 需求尤其要避免把实现方案过早写死。例如“必须使用 DMA”通常是设计决策，除非系统需求明确规定 CPU 占用或吞吐目标必须由 DMA 满足。）*

### A.4 SWE.2：把需求分解成可协作的软件架构

SWE.2 的第一性问题是：哪些职责必须分开，才能让需求可实现、可测试、可替换？

串口 HAL 可设计为以下构件：

| 构件 | 职责 | 主要接口 |
|------|------|----------|
| `UartHal` | 对上层提供稳定 API，隐藏芯片差异。 | `Uart_Init`、`Uart_Transmit`、`Uart_Read`、`Uart_GetStatus` |
| `UartHw` | 访问 MCU UART 寄存器。 | `UartHw_WriteReg`、`UartHw_ReadReg`、`UartHw_EnableIrq` |
| `UartBuffer` | 管理 TX/RX 环形缓冲。 | `RingBuffer_Push`、`RingBuffer_Pop` |
| `UartIrq` | 处理中断、错误标志和收发推进。 | `Uart_IrqHandler` |
| `UartConfig` | 保存通道、波特率、数据位、校验位等配置。 | 配置表或生成配置结构体 |

静态架构关注“有哪些块、接口是什么”。动态架构关注“这些块如何随时间协作”。例如发送流程：

1. 上层调用 `Uart_Transmit(UART_CH0, buf, len)`。
2. `UartHal` 检查通道状态与入参。
3. 数据写入 `UartBuffer` 的 TX 环形缓冲。
4. `UartHal` 使能 TX 空中断。
5. `UartIrq` 在中断中从 TX 缓冲取字节，调用 `UartHw` 写入数据寄存器。
6. 全部发送完成后，状态变为 `UART_IDLE` 或触发发送完成回调。

*（架构视角：这个拆分让寄存器访问集中在 `UartHw`，使单元测试可以用寄存器桩替代真实硬件；同时让缓冲算法、状态机和中断处理分别接受不同层级验证。）*

### A.5 SWE.3：把架构变成可编码的详细设计与单元

SWE.3 的第一性问题是：每个软件单元的输入、输出、状态、边界条件是否清楚到可以写代码和写单元测试？

示例详细设计片段：

| 软件单元 | 输入 | 输出 | 边界/错误 | 设计要点 |
|----------|------|------|-----------|----------|
| `Uart_Init` | 通道号、配置指针 | `UART_OK` / 错误码 | 空指针、非法通道、非法波特率 | 初始化寄存器、清状态、配置中断 |
| `Uart_Transmit` | 通道号、数据指针、长度 | `UART_OK` / `UART_BUSY` / `UART_E_PARAM` | 长度为 0、空指针、缓冲满 | 非阻塞，写入 TX 缓冲并启动发送 |
| `RingBuffer_Push` | 缓冲对象、字节 | 成功/失败 | 满缓冲 | 不覆盖未读数据 |
| `Uart_IrqHandler` | 通道号 | 无直接返回 | 错误标志、TX 空、RX 非空 | 处理中断标志并更新状态 |

一个可用于说明详细设计的接口片段：

```c
typedef enum {
    UART_OK = 0,
    UART_E_PARAM,
    UART_E_BUSY,
    UART_E_OVERFLOW,
    UART_E_HW_ERROR
} Uart_ResultType;

typedef enum {
    UART_BAUD_9600 = 9600,
    UART_BAUD_115200 = 115200
} Uart_BaudRateType;

typedef struct {
    Uart_BaudRateType baudRate;
    uint8_t dataBits;
    bool parityEnabled;
    uint8_t stopBits;
} Uart_ConfigType;

Uart_ResultType Uart_Init(uint8_t channel, const Uart_ConfigType *config);
Uart_ResultType Uart_Transmit(uint8_t channel, const uint8_t *data, uint16_t length);
Uart_ResultType Uart_Read(uint8_t channel, uint8_t *data, uint16_t maxLength, uint16_t *readLength);
Uart_ResultType Uart_GetStatus(uint8_t channel, Uart_StatusType *status);
```

费曼式理解：SWE.3 就是把“一个 UART HAL 构件”继续拆成“一个个可以被人读懂、可以被机器测试、可以被审查的函数和状态机”。

*（架构视角：详细设计必须说明中断上下文与任务上下文共享数据如何保护，例如关中断、原子操作、锁或单生产者单消费者环形缓冲。否则 SWE.5 集成阶段很容易出现偶发丢字节或死锁。）*

### A.6 SWE.4：证明每个软件单元自身正确

SWE.4 的第一性问题是：如果暂时不接真实硬件，每个函数是否按详细设计工作？

串口 HAL 单元验证示例：

| 单元 | 测试项 | 输入/场景 | 预期结果 |
|------|--------|-----------|----------|
| `Uart_Init` | 合法配置初始化 | `UART_CH0` + `115200 8N1` | 返回 `UART_OK`，寄存器桩记录正确配置 |
| `Uart_Init` | 空指针防护 | `config == NULL` | 返回 `UART_E_PARAM`，不访问寄存器 |
| `Uart_Transmit` | 非阻塞发送 | 3 字节数据 | 返回 `UART_OK`，TX 缓冲长度为 3 |
| `RingBuffer_Push` | 满缓冲处理 | 缓冲已满再写入 | 返回失败，不覆盖旧数据 |
| `Uart_IrqHandler` | RX 错误处理 | 注入帧错误标志 | 清除错误标志，记录 `UART_E_HW_ERROR` 或具体错误 |

示例单元测试伪代码：

```c
void test_Uart_Init_Configures115200_8N1(void)
{
    Uart_ConfigType cfg = {
        .baudRate = UART_BAUD_115200,
        .dataBits = 8,
        .parityEnabled = false,
        .stopBits = 1
    };

    FakeUartHw_Reset();

    Uart_ResultType result = Uart_Init(0u, &cfg);

    TEST_ASSERT_EQUAL(UART_OK, result);
    TEST_ASSERT_EQUAL(FAKE_UART_BAUD_115200_DIV, FakeUartHw_GetBaudDiv(0u));
    TEST_ASSERT_FALSE(FakeUartHw_IsParityEnabled(0u));
}
```

*（架构视角：SWE.4 不应只做 happy path。嵌入式 HAL 的缺陷高发区是非法入参、状态转换、边界长度、缓冲满/空、中断标志竞争和错误标志清除顺序。）*

### A.7 SWE.5：证明构件集成后仍能协作

SWE.5 的第一性问题是：单元都对了，组合起来是否仍然对？

串口 HAL 的集成对象可以是 `UartHal + UartBuffer + UartHwStub + UartIrq`。集成验证不再只看单个函数，而要看接口、顺序、状态和时序。

示例集成验证场景：

| 集成场景 | 集成元素 | 预期 |
|----------|----------|------|
| 非阻塞发送链路 | `Uart_Transmit` + TX 缓冲 + TX 中断处理 | 调用后数据进入缓冲；连续触发 TX 空中断后，硬件桩收到完整字节序列 |
| 接收链路 | RX 中断 + RX 缓冲 + `Uart_Read` | 硬件桩注入字节后，上层能按顺序读取 |
| 错误上报 | 硬件错误标志 + `Uart_IrqHandler` + 状态查询 | 帧错误/溢出错误能被记录并上报 |
| 回归场景 | 修改缓冲大小或中断策略 | 原有发送、接收、错误处理用例仍通过 |

示例集成测试伪代码：

```c
void test_Uart_Transmit_IsCompletedByTxInterrupts(void)
{
    uint8_t payload[] = {0x12u, 0x34u, 0x56u};
    Uart_Init(0u, &g_UartConfig_115200_8N1);

    TEST_ASSERT_EQUAL(UART_OK, Uart_Transmit(0u, payload, 3u));

    FakeUartHw_SetTxEmpty(0u, true);
    Uart_IrqHandler(0u);
    Uart_IrqHandler(0u);
    Uart_IrqHandler(0u);

    TEST_ASSERT_EQUAL_UINT8(0x12u, FakeUartHw_GetTxByte(0u, 0u));
    TEST_ASSERT_EQUAL_UINT8(0x34u, FakeUartHw_GetTxByte(0u, 1u));
    TEST_ASSERT_EQUAL_UINT8(0x56u, FakeUartHw_GetTxByte(0u, 2u));
    TEST_ASSERT_EQUAL(UART_IDLE, Uart_GetInternalState(0u));
}
```

*（架构视角：SWE.5 的价值在于暴露“接口没有说清楚”的问题。例如中断是否可重入、发送完成状态何时置位、RX 缓冲满时丢新数据还是丢旧数据，这些通常不是单元测试能完整覆盖的。）*

### A.8 SWE.6：证明完整软件满足软件需求

SWE.6 的第一性问题是：站在需求角度看，集成后的 UART HAL 是否真的满足 SWE.1 写下的每条软件需求？

示例需求到验证的闭环：

| 软件需求 | SWE.6 验证措施 | 通过准则 |
|----------|----------------|----------|
| `SWE1-UART-001` 初始化接口 | 在目标板或寄存器仿真环境调用 `Uart_Init` | 返回成功，串口可发送/接收 |
| `SWE1-UART-002` 支持 115200/9600 | 用示波器、逻辑分析仪或仿真寄存器确认波特率 | 波特率误差在项目允许范围内 |
| `SWE1-UART-003` 非阻塞发送 | 测量 `Uart_Transmit` 调用耗时 | 小于 `100 us`，且数据最终完整发出 |
| `SWE1-UART-004` 错误报告 | 注入帧错误、溢出、奇偶错误 | 上层获得对应错误信息 |
| `SWE1-UART-005` 隔离寄存器访问 | 静态检查和代码审查 | 应用层无直接寄存器访问 |

费曼式理解：SWE.6 就是拿着最开始的“愿望清单”逐条验收，而不是拿着代码证明代码自己没问题。

*（架构视角：SWE.6 对 HAL 很关键，因为真正风险往往与目标环境有关。PC 单元测试不能替代目标板上的波特率误差、时钟配置、中断优先级、DMA cache 一致性和功耗模式唤醒验证。）*

### A.9 六个 SWE 过程之间的证据链

一个清晰的证据链可表示为：

```text
系统需求 / HSI
  -> SWE.1 软件需求
  -> SWE.2 软件架构
  -> SWE.3 详细设计与代码
  -> SWE.4 单元验证
  -> SWE.5 构件与集成验证
  -> SWE.6 软件需求级验证
```

对串口 HAL 来说，一个最小追溯示例为：

| 链路 | 示例 |
|------|------|
| 系统需求 | ECU 需要通过 UART 与诊断设备通信。 |
| 软件需求 | `SWE1-UART-003`：发送接口必须非阻塞，`100 us` 内返回。 |
| 架构 | `UartHal` 接口层 + `UartBuffer` 缓冲 + `UartIrq` 中断发送。 |
| 详细设计 | `Uart_Transmit` 只拷贝到 TX 缓冲并使能 TX 空中断。 |
| 单元验证 | 测试 `Uart_Transmit` 返回时间、缓冲写入、忙状态。 |
| 集成验证 | 触发 TX 中断后硬件桩收到完整字节序列。 |
| 软件验证 | 目标板测量接口返回时间并确认串口帧完整发出。 |

## 附录 B：SWE.1-SWE.6 详细实践指导：以串口 HAL 驱动为例

本章从“实际要做哪些工作”的角度，给出一个可执行的 SWE.1-SWE.6 落地流程。示例对象为 `UART HAL` 驱动，假设项目采用 C 语言、MCU 裸机或 RTOS 环境，并支持中断驱动收发。

### B.1 项目输入与范围假设

开始 SWE 工作前，应先明确输入边界：

| 输入项 | 示例 |
|--------|------|
| 系统需求 | ECU 通过 UART 与诊断设备通信。 |
| HSI / 芯片资料 | UART0 基地址、IRQ 号、时钟源、寄存器位定义。 |
| 平台约束 | CPU 主频 `80 MHz`，UART 时钟 `40 MHz`，中断优先级低于安全关键控制中断。 |
| 编码规则 | MISRA C、项目命名规范、无动态内存。 |
| 发布范围 | 本次只交付 UART0，支持轮询初始化、中断收发，不支持 DMA。 |

*（架构视角：把“不支持 DMA”“只交付 UART0”写入发布范围，可以防止评审时把未来能力误当成本次缺陷。）*

### B.2 SWE.1 实践指导：软件需求分析

需要做的工作：

1. 从系统需求、HSI、芯片手册和上层软件使用场景提取 UART HAL 软件需求。
2. 给每条需求分配唯一 ID、优先级、发布范围、验证准则。
3. 分析需求是否正确、完整、可实现、可验证。
4. 分析对运行环境的影响，例如中断、时钟、功耗、内存、调度。
5. 建立需求到系统需求/HSI/架构输入的追溯。
6. 与上层软件、系统工程、测试、硬件团队确认需求。

示例需求条目：

| 字段 | 内容 |
|------|------|
| ID | `SWE1-UART-003` |
| 标题 | 非阻塞发送 |
| 描述 | UART HAL 应提供 `Uart_Transmit(channel, data, length)`；当通道已初始化且 TX 缓冲有足够空间时，该接口应复制数据到 TX 缓冲并在 `100 us` 内返回。 |
| 优先级 | 必须 |
| 约束 | 不使用动态内存；不在接口中等待完整发送完成。 |
| 验证准则 | 单元测试验证状态和缓冲；目标板测试测量 API 返回时间；集成测试验证中断发送完整性。 |
| 追溯 | `SYS-COM-001`、`HSI-UART0-IRQ` |

常见检查清单：

- 每条需求是否能设计、实现和测试。
- 是否区分功能需求与非功能需求。
- 是否说明错误处理，例如非法通道、空指针、缓冲满、硬件错误。
- 是否说明并发假设，例如接口是否可在中断中调用。
- 是否说明资源约束，例如 TX/RX 缓冲大小。

### B.3 SWE.2 实践指导：软件架构设计

需要做的工作：

1. 定义软件构件及职责边界。
2. 定义构件接口、数据流和控制流。
3. 定义静态结构，例如模块、文件、配置表、依赖方向。
4. 定义动态行为，例如初始化、发送、接收、错误处理、中断流程。
5. 分析架构决策，例如为什么选中断而不是阻塞发送或 DMA。
6. 建立软件架构与软件需求之间的一致性和双向追溯。

示例架构决策记录：

| 决策项 | 内容 |
|--------|------|
| 决策 ID | `ADR-UART-001` |
| 决策 | 本版本采用中断驱动发送，不采用阻塞发送或 DMA。 |
| 原因 | 满足 `100 us` 非阻塞返回要求；吞吐量低于 DMA 必需阈值；实现复杂度适合当前发布范围。 |
| 影响 | 需要 TX 环形缓冲；需要处理中断与任务上下文共享数据；需要集成验证中断发送链路。 |
| 追溯 | `SWE1-UART-003`、`SWE1-UART-004` |

示例架构关系：

```text
Application
  -> UartHal API
      -> UartBuffer
      -> UartIrq
      -> UartHw
          -> MCU UART registers
```

示例动态流程：接收错误处理

```text
UART hardware sets frame error flag
  -> UART IRQ occurs
  -> Uart_IrqHandler reads status register
  -> UartIrq maps hardware flag to UART_E_FRAME
  -> UartHal stores error status or calls upper callback
  -> Upper layer reads status and performs recovery
```

### B.4 SWE.3 实践指导：详细设计与单元构建

需要做的工作：

1. 为每个构件拆分软件单元。
2. 描述每个单元的输入、输出、状态、前置条件、后置条件。
3. 定义数据结构、枚举、状态机和错误码。
4. 说明上下文限制，例如哪些函数可在 ISR 调用，哪些只能在任务上下文调用。
5. 按编码准则实现代码。
6. 建立详细设计、源代码、架构、需求之间的追溯。

示例状态机：

```text
UART_UNINIT
  -- Uart_Init OK --> UART_IDLE
UART_IDLE
  -- Uart_Transmit accepted --> UART_TX_ACTIVE
UART_TX_ACTIVE
  -- all bytes sent --> UART_IDLE
Any initialized state
  -- hardware error --> UART_ERROR
UART_ERROR
  -- Uart_ClearError --> UART_IDLE
```

示例详细设计规则：

| 规则 ID | 规则 |
|---------|------|
| `DD-UART-001` | `Uart_Init` 未成功前，除 `Uart_GetStatus` 外的 API 应返回 `UART_E_UNINIT`。 |
| `DD-UART-002` | `Uart_Transmit` 不直接轮询等待发送完成，只写入 TX 缓冲并使能 TX 空中断。 |
| `DD-UART-003` | `Uart_IrqHandler` 应先读取并保存状态寄存器，再清除硬件错误标志。 |
| `DD-UART-004` | TX/RX 环形缓冲写指针与读指针更新必须避免中断竞争。 |

示例实现片段：

```c
Uart_ResultType Uart_Transmit(uint8_t channel, const uint8_t *data, uint16_t length)
{
    if ((channel >= UART_CHANNEL_COUNT) || (data == NULL) || (length == 0u)) {
        return UART_E_PARAM;
    }

    if (g_uartState[channel] == UART_UNINIT) {
        return UART_E_UNINIT;
    }

    if (RingBuffer_Free(&g_uartTxBuffer[channel]) < length) {
        return UART_E_BUSY;
    }

    Uart_EnterCritical(channel);
    for (uint16_t i = 0u; i < length; i++) {
        (void)RingBuffer_Push(&g_uartTxBuffer[channel], data[i]);
    }
    g_uartState[channel] = UART_TX_ACTIVE;
    UartHw_EnableTxEmptyIrq(channel);
    Uart_ExitCritical(channel);

    return UART_OK;
}
```

*（架构视角：示例代码体现详细设计意图，但真实项目还要根据 MISRA 规则处理强制类型转换、返回值使用、临界区嵌套和硬件抽象层命名。）*

void test_Uart_RxInterrupt_MakesDataAvailableToUpperLayer(void)

### B.10 评审时可用的判断准则

评审 SWE.1-SWE.6 是否真正落地，可以问以下问题：

1. 是否能从任意一条 UART 需求追溯到架构、详细设计、代码和验证结果？
2. 是否所有公开 API 都定义了非法入参、未初始化、忙状态和硬件错误行为？
3. 是否明确哪些代码运行在中断上下文，哪些运行在任务上下文？
4. 是否验证了缓冲满、缓冲空、连续中断、错误标志和回归场景？
5. 是否在目标环境验证了波特率、返回时间和实际收发行为？
6. 是否记录了架构决策及其理由，例如中断、轮询或 DMA 的选择？
7. 是否能证明“有追溯链接”同时也“内容一致”？

*（架构视角：一个成熟的 SWE 实践不是追求文档数量，而是追求每个关键设计选择都有理由、每个风险点都有验证、每个变更都能分析影响。）*
